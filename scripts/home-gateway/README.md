# Домашний шлюз на Linux

Личные переносимые исходники. Устройства, адреса, результаты диагностики и
готовые конфигурации хранятся отдельно в `.local-only/`. Ключи SSH и параметры
доступа к VPS не включаются в исходники.

`inspect.sh` собирает сведения о существующей системе, интерфейсах и сетевых
службах. Он ничего не устанавливает и не меняет.

`build_config.py` готовит конфигурацию sing-box 1.14. Перед установкой нужны
проверенные LAN-адрес, имя Ethernet-интерфейса и DNS. Конфигурация Linux TUN
не должна запускаться на Mac. Проверка `sing-box check` не изменяет сеть.

Режим `direct` предназначен для проверки шлюза до VPS: весь поддерживаемый
IPv4-трафик идёт напрямую. Режим `rules` использует подготовленный AWG-интерфейс
или ранее настроенный VLESS outbound. Политика содержит `.ru`, `.рф`,
исключения для прямого/VPN-доступа и IPv4-адреса устройств, которым нужен
полностью прямой доступ. Домены нормализуются в IDNA.

Для доменных правил устройства должны использовать DNS шлюза; произвольный
DoH/DoT внутри приложений требует отдельного решения. VLESS не переносит ICMP:
в режиме правил ICMP к иностранным адресам блокируется, а не выходит напрямую.
Для начальной установки предполагается отключённый IPv6 на основном роутере.
DNS reverse_mapping связывает реальные IP прямых доменов с именами для
маршрутизации; FakeIP engine сохраняется и в direct, чтобы уже выданные
виртуальные адреса оставались распознаваемыми при отключении VPN.

Установка на плату производится после диагностики и сохранения текущих настроек.
Нужны Linux с TUN, nftables/nfqueue и systemd, Python 3, iproute2 и официальный
sing-box. Установка sing-box через подписанный APT-репозиторий описана в
https://sing-box.sagernet.org/installation/package-manager/.

Схема с одним Ethernet-портом требует продуманной обратной маршрутизации и
отключения ICMP redirects; данный генератор не включает IP forwarding, NAT,
DHCP, systemd или настройки роутера автоматически. Перед переключением
домашнего DHCP проверяется одно устройство. Возврат основного шлюза и DNS на
исходный роутер восстанавливает обычный доступ при выключенной плате.

Способ восстановления: скопировать этот каталог, поставить зависимости из
официальных репозиториев, повторить диагностику и подготовить конфигурацию
с проверенными параметрами сети. Не восстанавливать настройки вслепую.

## Подготовка USB-восстановления eMMC с Mac

`build_rkdeveloptool.py` собирает исходники официального
https://github.com/rockchip-linux/rkdeveloptool с установленными Command Line
Tools и libusb (`brew install libusb`, если его нет). Исходный snapshot и
скомпилированная копия остаются в локальном каталоге вне переносимых исходников.
В копии меняются константные размеры буферов для совместимости с Clang и
исправляется индекс LOADER1/LOADER2 в parser функции упаковки и устанавливается
USB-таймаут 10 секунд вместо бесконечного; версия берётся
из официального CMake-файла (1.3). Исходный snapshot сохраняется неизменным.
Также расширяется длина RC4 в старом упаковщике: современные компоненты
DDR/UsbPlug могут превышать 64 КиБ. Собранные компоненты проверяются обратным
декодированием перед попыткой USB-загрузки.

Скрипт сборки не выполняет команд USB и не записывает eMMC. После сборки
`rkdeveloptool ld` обнаруживает платы, а `rfi` читает параметры накопителя.
Запись выполняется отдельно, только после идентификации платы и проверки
официального образа именно для этой модели. Не использовать команды стирания
или записи при нескольких подключённых Rockchip-устройствах.

## Подготовка SSH в новом образе Armbian

`prepare_armbian_image.py` добавляет отдельный публичный Ed25519-ключ в
официальный образ Orange Pi 4 LTS, проверяет seed-файлы и создаёт отдельную
копию образа. Он не записывает устройства. Для первого запуска задаются
случайные пароли root и обычного пользователя gateway, язык en_US.UTF-8 и
часовой пояс Europe/Moscow. Ethernet остаётся на DHCP.

`bootstrap_board.sh` выполняется один раз механизмом Armbian first-login,
добавляет тот же ключ обычному пользователю и устанавливает имя home-gateway.
Парольный вход SSH отключён; root доступен по ключу для настройки шлюза.

В персонализированном образе есть временные пароли, поэтому рабочий каталог
должен быть за пределами Git. Скрипт проверяет это. Приватный ключ сохраняется
в обычном SSH-каталоге компьютера, не в исходниках. Файл initial-passwords.txt
в приватном рабочем каталоге предназначен для восстановления доступа;
перед очисткой рабочего каталога его следует сохранить в менеджере паролей.

Источник механизма first-login:
https://docs.armbian.com/user-guide/autoconfig/.

Опция `--usb-access` включает служебный CDC-ECM интерфейс USB-C с адресом
169.254.77.1/16 для настройки без Ethernet и Wi-Fi. Нужны USB gadget/ECM в
ядре и включённый OTG-контроллер в Device Tree; для другого образа проверку
ядра в скрипте нужно актуализировать. Mac получает собственный link-local
адрес автоматически; эта сеть не задаёт default route и не раздаёт интернет.
Служба и файл systemd-networkd включаются только в создаваемую копию образа.
USB-доступ можно убрать после установки: отключить `home-gateway-usb.service`,
удалить соответствующий `.network` и перезагрузить плату.
Источник механизма USB gadget: https://docs.kernel.org/usb/gadget_configfs.html.

## Начальная установка шлюза

`install_board.sh` предназначен для первой установки после диагностики,
закрепления DHCP-адреса и проверки официального ARM64-пакета sing-box.
Аргументы: каталог этих исходников, отдельный локальный NETWORK_JSON
(`lan_ip`, `lan_cidr`, `interface`, `upstream_dns`) и проверенный `.deb`.
В текущем установщике Netplan рассчитан на единственный интерфейс eth0;
другая схема требует явного пересмотра. `upstream_dns` здесь одновременно
является адресом основного роутера. Существующая настройка шлюза не затирается.
Установщик сохраняет прежний Netplan, фиксирует MAC и собственный маршрут
платы через основной роутер, проверяет конфигурацию и оставляет службы
неактивными до отдельной проверки. DNS клиентов должен указывать на плату.

`network_guard.py` включает forwarding, отключает ICMP redirects и управляет
только двумя собственными таблицами nftables. В режиме rules прямой запасной
маршрут через основной роутер блокируется, даже если sing-box остановится.
В режиме direct этот маршрут доступен. Для запуска нужно включить
home-gateway-network.service и sing-box.service после проверки на одном клиенте.

`sudo gatewayctl direct` — всё напрямую. `sudo gatewayctl trial --seconds 180`
(и alias `rules`) включает правила только после отдельного разрешения владельца
и изолированной проверки кандидата. До `gatewayctl confirm` действует откат по
таймеру. `status` и `policy` показывают состояние.
`domain direct example.com`, `domain vpn example.ru`, `domain remove example.com`
управляют исключениями с поддоменами. `client direct IP` и `client remove IP`
управляют исключением устройства. Изменения исключений сохраняются для следующего
явного включения и не меняют живую сеть. После них повторить изолированную проверку.
Контроллер проверяет конфигурацию sing-box до применения и откатывает неудачный запуск.
Опциональный `gatewayctl auto-return on` после отдельного разрешения владельца
возвращает уже подтверждённый AWG после аварийного отката: минимум пять минут
стабильных независимых проверок и пауза при повторных сбоях. Ручной `direct`
отменяет автовозврат. Порядок и ограничения описаны в HOME_READY.md.
Рабочая конфигурация VPS хранится отдельно в /etc/home-gateway/vps-outbound.json,
доступна только root и не включается в эти исходники.

`verify_packets.sh` проверяет настоящий sing-box через отдельный клиентский
network namespace, затем моделирует однопортовый LAN с отдельными клиентом,
шлюзом и роутером. Проверяются DNS/HTTPS, адрес после NAT, блокировка прямого
запасного выхода и возврат direct. Запускать от root в режиме direct до
переключения домашних клиентов: служба временно перезапускается, её исходная
конфигурация восстанавливается. Нужны iproute2, curl и dnsutils. Тестовые
namespaces удаляются; совпадающие существующие имена не используются.

`dhcp_inform.py --interface IFACE --client-ip CURRENT_IP` читает реально
выдаваемые DHCP-опции шлюза и DNS, не меняя аренду. Требует root/CAP_NET_RAW.
После смены DHCP домашним устройствам нужен renew или переподключение Wi-Fi.
Пустое поле запасного DNS на некоторых роутерах добавляет DNS самого роутера;
нужно проверить ответ DHCP, а не только форму настроек.

## VPS и проверка без переключения домашней сети

На новом VPS сначала проверить SSH по отдельному ключу и доступность HTTPS
сайта, выбранного для REALITY handshake. Установить sing-box из официального
подписанного APT-репозитория по инструкции выше, а также python3, ufw и iproute2.
Проверить отсутствие действующих сервисов на TCP 443 и ненужного экземпляра
стандартного sing-box.service. `install_vps.sh SOURCE_DIR PUBLIC_IPV4 SERVER_NAME`
предназначен только для нового сервера: создаёт собственный home-vps.service
с VLESS/REALITY на TCP 443, разрешает SSH и этот порт в UFW, запрещает входящие
соединения на остальные порты. SSH-пароль можно отключать только после
успешной отдельной проверки входа по ключу. Скрипт не меняет SSH самостоятельно.

Unit-файлы `home-vps.service` и `home-vps-probe.service` разрешают AF_NETLINK:
sing-box читает через него состояние сетевых интерфейсов даже без TUN.
Прав CAP_NET_ADMIN у этих служб нет. Установщики проверяют появление портов
после старта; окончательная проверка — настоящий запрос через туннель.

`harden_vps_ssh.sh` запускается отдельным шагом через уже проверенный root SSH
по ключу. Он отключает парольный и keyboard-interactive вход, проверяет
эффективную конфигурацию sshd и перезагружает только её. При ошибке удаляет
собственный новый drop-in. Перед закрытием текущей сессии проверить второе
независимое подключение по ключу. Пароль локальной консоли VPS не меняется.

`vps_config.py` генерирует UUID и ключ REALITY на самом VPS, проверяет JSON
через установленный sing-box и отказывается сохранять секреты в Git checkout.
Файлы сервера и клиента находятся в /etc/home-vps; их нельзя копировать в этот
репозиторий. Для переноса vps-outbound.json на Orange Pi использовать закрытый
SSH-канал без вывода содержимого в лог и без промежуточного файла в исходниках.

На Orange Pi `install_probe.sh SOURCE_DIR PRIVATE_VPS_OUTBOUND` сохраняет
root-only профиль для будущего режима rules, но не меняет текущий config.json,
маршруты, nftables, домашний DNS или режим шлюза. Он запускает отдельный
home-vps-probe.service без сетевых привилегий: SOCKS/HTTP слушает только
127.0.0.1:18080, тестовый DNS — только 127.0.0.1:1053. Локальный DNS-порт
проверяет передачу UDP через VLESS. `verify_vps_probe.sh` проверяет внешний IP,
HTTPS и DNS, совпадение внешнего IP с настроенным VPS, а также сохранение
режима direct до и после проверки.

`verify_vps_loopback.py` до выдачи VPS проверяет тот же протокол настоящими
пакетами между двумя временными экземплярами sing-box на 127.0.0.1. Проверяет
TLS/REALITY/Vision, HTTPS и UDP/DNS; временные ключи остаются вне Git и удаляются
вместе с тестовым каталогом, процессы завершаются при успехе и ошибке. Нужны
свободные TCP-порты 18443/18081 и DNS-порт 1053. Тест не заменяет проверку
реального пути до VPS у домашнего провайдера и не меняет маршруты домашней сети.

Наличие рабочего пробного подключения не разрешает переключать домашний
трафик. Режим rules включать отдельно, после явного согласования с владельцем
сети. Для остановки только проверки: systemctl stop home-vps-probe.service.

`vpn-off.command` — запускаемая пользователем кнопка отключения VPN для macOS.
Нужны установленный SSH alias home-gateway и ключ на самом Mac; ничего
секретного в файл не помещается. По умолчанию используется
~/.ssh/home-gateway.config; другой путь можно задать HOME_GATEWAY_SSH_CONFIG.
Скрипт не запускается автоматически и не обеспечивает обход выключенной платы.

Если провайдер не установил переданный при заказе публичный SSH-ключ,
`bootstrap_vps_key.sh PUBLIC_IPV4 PUBLIC_KEY_FILE PINNED_KNOWN_HOSTS` запускается
владельцем в интерактивном Terminal. Существующий пароль из письма провайдера
вводится прямо в SSH, не передаётся через чат и не сохраняется скриптом.
Проверка host key остаётся строгой, используется ранее закреплённый файл.
Скрипт добавляет только проверенный публичный ключ root и не меняет пароль.

## Дополнительный AmneziaWG и сравнение без переключения дома

Проверка дополнительного UDP-порта при потерях на пути до VPS и порядок
сохранения/отката описаны в [PORT_ALIAS.md](PORT_ALIAS.md). Шаблон не применяется
автоматически; создание нового сетевого доступа требует отдельного разрешения.

AWG 3.1 работает отдельной службой и использует UDP 443; VLESS остаётся на
TCP 443. Нужны Python 3, systemd, iproute2, TUN, curl, iptables и ufw на VPS.
Используется userspace `amneziawg-go`: установщик не добавляет модуль ядра,
DKMS или новую прошивку. Нагрузка CPU такого варианта должна оцениваться
на настоящем устройстве и не равна производительности реализации в ядре.

`build_awg.sh NEW_PRIVATE_BUILD_DIRECTORY` запускается на Linux x86_64.
Он проверяет SHA256 официального Go 1.27.2 и опубликованного пакета CLI,
собирает Go-реализацию для amd64 и arm64 из закреплённого исходника:

- amneziawg-go v3.1.20260828: commit
  `b5928efb6ca19f0153958460c3d141f04abc5c2e`;
- amneziawg-tools v3.1.20260812: commit
  `ee0f0a9aa34ff0a0da4b3433b9512781cfe02843`.

Сборку выполнять в новом каталоге. Кэш исходников не предназначен для
переключения между версиями. Зависимости сборки на VPS: tar, gzip, curl,
Python 3 с zipfile, сертификаты TLS и доступ к официальным Go/GitHub-модулям.
Копировать `output/amneziawg-go-amd64` или `output/amneziawg-go-arm64` как
`/usr/local/bin/amneziawg-go`, режим 0755. Официальный `output/awg-amd64`
устанавливается как `/usr/local/bin/awg` на VPS. На ARM64 нужны make, gcc и
заголовки libc (`build-essential` в Debian): распаковать закреплённый
`awg-tools-source.tar.gz`, выполнить `make -C src -j2` и установить полученный
`src/wg` как `/usr/local/bin/awg`, режим 0755. Проверить хеши перед передачей
и после неё. Если зеркало APT недоступно, не менять глобальную сеть платы:
для одной установки можно явно передать APT HTTP/HTTPS proxy уже проверенного
loopback-прокси и ограничить тайм-аут/повторы. Не оставлять этот proxy в APT
постоянно и не прерывать работающий dpkg.

`install_awg_server.sh SOURCE_DIR VERIFIED_PUBLIC_IPV4` предназначен для
первой установки на подготовленный VPS. Отказывается затирать существующие
конфигурации. `awg_config.py` создаёт отдельные пары ключей и PSK для Orange Pi
и iPhone; приватные конфигурации остаются в `/etc/home-awg`, вне Git.
Параметры AWG 3.1 сверены с официальным amnezia-client 5.0.3.0, commit
`de93650a90739b87bb47a632872ea9d0adc9412f`. Изменение профилей вручную требует
согласованности параметров на сервере и клиенте.

Серверная служба `home-awg.service` создаёт только `awgsrv0` и включает
IPv4 forwarding. Файрвол разрешает UDP 443 и forwarding из AWG-подсети на
проверенный WAN-интерфейс. `awg_runtime.py` добавляет/удаляет только своё
правило MASQUERADE с комментарием `home-awg-only`; чужие таблицы не очищаются.
Серверная служба включается для автозапуска. Проверить её перезапуск и
настоящую передачу HTTPS/DNS до использования профиля на клиентах.

Для Orange Pi передать `orange-device.conf` напрямую по SSH, без печати
ключей в журнал и без промежуточного файла в репозитории. Затем выполнить
`install_awg_probe.sh SOURCE_DIR PRIVATE_DEVICE_CONFIGURATION`. Текущая
домашняя конфигурация должна быть в режиме direct.

Проба AWG изолирована в network namespace `home-awg-test`: default route и
DNS задаются только там. UDP-сокет создаётся в основном namespace с mark
0x2024 для обхода существующего TUN, затем интерфейс перемещается в тестовый
namespace. Хостовые маршруты, DNS и основной конфиг не переключаются.
Отдельная `home-awg-probe-network.service` закрепляет namespace до запуска
защищённой службы `home-awg-probe.service`. Это важно для видимости namespace
между процессами при systemd PrivateTmp/ProtectSystem.

Обе тестовые AWG-службы запускаются вручную и не включаются для автозагрузки.
Проверка: `python3 /usr/local/lib/home-awg/awg_runtime.py verify-baseline`.
Тестовые команды выполняются явно через `ip netns exec home-awg-test ...`.
Остановить пробу и освободить namespace:
`systemctl stop home-awg-probe.service home-awg-probe-network.service`.
Сервер при этом продолжает обслуживать iPhone. Конфигурация в
`/etc/netns/home-awg-test` остаётся для повторного старта; не удалять чужие
namespace, интерфейсы или DNS-каталоги.

`benchmark_vpn.py --output NEW_REPORT.json` выполняет чередующиеся запросы
через AWG namespace и VLESS SOCKS. Проверяет прямой режим и неизменность
конфига/маршрутов до и после серии. В тестах Cloudflare фиксируется один
IPv4 на endpoint, используется HTTP/1.1 и новый процесс curl для каждого
запроса. «Задержка» в отчёте — полное время свежего HTTPS-запроса, не ICMP ping.
Отчёт содержит отдельные результаты больших загрузок, HTTP-коды, тайм-ауты,
нагрузку процессов в процентах одного ядра и температуру. HTTP 403 сервера
загрузок не доказывает отказ VPN; такие ответы нужно учитывать отдельно и
проверять на другом источнике. `--large-only` повторяет две большие загрузки
каждым протоколом без повтора остальной серии. Это краткие измерения из
данной сети, не гарантия пропускной способности или длительной стабильности.

## Отдельные профили iPhone и проверка Xray

`add_vless_client.py DEVICE_NAME` на VPS создаёт отдельную учётную запись и
приватную ссылку VLESS в `/etc/home-vps/clients`. Проверяет кандидат
конфигурации, сохраняет предыдущую версию и перезапускает только сервер
VLESS с откатом при ошибке запуска. Не заменяет уже существующий профиль.

`export_iphone_profiles.sh SSH_CONFIG NEW_PRIVATE_DIRECTORY` запускается на
Mac и сохраняет AWG `.conf` и Happ `.txt` вне всех Git-каталогов с правами
0700/0600. Отправить AWG-файл на iPhone через AirDrop и импортировать в
приложение AmneziaWG с поддержкой AWG 3.1; VLESS-ссылку импортировать в Happ.
Включать для проверки один VPN за раз. Эти файлы дают доступ к личному VPS;
в инвентаре хранить только пути к ним. Не отправлять их сторонним QR-сервисам.

`make_happ_profile.py --outbound PRIVATE_OUTBOUND --output NEW_PRIVATE_JSON`
создаёт небольшой профиль `Home-NL-iphone-Clean` с теми же учётными данными.
В нём явно задано логирование Info, DNS IPv4, loopback SOCKS/HTTP и единственный
VLESS outbound. Геобазы, sniffing и mux не используются. Он предназначен для
отдельной диагностики iPhone и направляет весь трафик через VPS. Существующие
профили и сервер не меняются. Особенности iOS TUN и его DNS проверяются на
телефоне отдельно: успешный Linux-тест их не подтверждает.

`private_qr.swift INPUT_JSON NEW_PNG` создаёт QR локально средствами CoreImage
и проверяет его обратным декодированием. Нужны macOS, Swift Command Line Tools,
CoreImage, ImageIO и UniformTypeIdentifiers. Запускать через
`swift -module-cache-path PRIVATE_CACHE scripts/home-gateway/private_qr.swift ...`
с `umask 077` и каталогом назначения вне Git. QR содержит приватный профиль;
не добавлять PNG или JSON в репозиторий. Обратное декодирование QR проверяет
только сохранность данных. Опция `--text` вместо JSON читает UTF-8, например
настоящую ссылку подписки. В проверенном пути добавления Happ 6.1.0 на iPhone
и сканер, и использованный пункт импорта из буфера отвергают сырой JSON
сообщением о невозможности создать URL из строки. Для этого пути нужен URL
подписки, отдающий JSON-массив. Обычная VLESS-ссылка и JSON — разные форматы.

`private_profile_server.py` и `home-vpn-import.service` дают разовый импорт
проверенного JSON через уже работающую AmneziaWG. Установить исходник в
`/usr/local/lib/home-vps/`, unit в systemd, затем от root выполнить
`python3 /usr/local/lib/home-vps/private_profile_server.py prepare` и
`systemctl start home-vpn-import.service`. Подготовка создаёт приватные
`token` и `url.txt` в `/etc/home-vps/private-import`; значения не печатаются
и не копируются в Git. Временный сервер слушает только AWG-адрес и требует
случайный токен. HTTP идёт внутри зашифрованного AWG, публичного listener нет.
В ответе JSON-массив с одним ранее проверенным профилем и явные заголовки
`socks-auth-mode: from-json`, `http-auth-mode: from-json`.

Unit получает профиль и токен через systemd LoadCredential, работает без root,
не включается для автозагрузки и останавливается через 15 минут. Только его
root helpers добавляют/удаляют одно помеченное правило INPUT для AWG-интерфейса
и подсети. Остановка должна удалять и listener, и своё правило; проверить это
до выдачи URL владельцу. Для ручной остановки:
`systemctl stop home-vpn-import.service`. Нужны systemd с LoadCredential,
Python 3.9+, iptables, существующий AWG и сервисный пользователь sing-box.
Этот URL доступен iPhone с включённой AmneziaWG: сначала импортировать подписку,
затем выключить AWG и проверить подключение Happ. После окончания окна выдачи
URL потребуется явный повторный запуск для обновления; постоянная раздача
профилей не включается. Не переносить этот HTTP listener на публичный адрес.

`verify_xray_client.py --binary VERIFIED_XRAY --outbound PRIVATE_OUTBOUND`
проверяет существующий sing-box VLESS outbound настоящим Xray. Нужен
официальный Linux-бинарник для архитектуры платы с проверенным SHA256
release asset; его скачивание и запуск выполняются отдельно. Проба временно
слушает SOCKS только на loopback, использует тот же mark 0x2024 и не создаёт
TUN/маршруты. Конфигурация и подробный журнал находятся во временном приватном
каталоге `/run` и удаляются при штатном завершении или SIGTERM. В выводе
только синтетические запросы, категории ошибок и очищенная сводка. Дополнительно
проверяется настоящий DNS-запрос через SOCKS UDP association и VLESS. Для
повтора можно явно выбрать свободный `--port`. Такой тест проверяет профиль
и Xray на плате; он не проверяет iOS TUN и настройки конкретного Happ.
Вместо `--outbound` можно передать `--config PRIVATE_XRAY_JSON`: тогда проверяется
подготовленный JSON с временной заменой локального inbound и добавлением Linux
SO_MARK только в диагностическую копию. В экспорт для iPhone SO_MARK не входит.

Мониторинг существующей AWG-пробы вынесен в самостоятельный модуль
[`../vpn-monitor/`](../vpn-monitor/README.md). Он проверяет DNS/HTTPS/выходной IP
каждые пять минут, хранит историю и события, собирает официальные релизы раз в
неделю и предоставляет локальный API для будущей общей админки. В режиме
подготовки домашняя маршрутизация остаётся `direct`. Монитор поддерживает
разрешённые режимы `direct` и `rules`, проверяя неизменность в пределах опроса.
Включение домашнего VPN требует отдельного согласования.

Домашний AWG, локальный сторож, аварийный DNS и новая маршрутизация описаны в
[HOME_READY.md](HOME_READY.md). `verify_home_ready.py` использует отдельного
виртуального клиента и службу; основную домашнюю службу он не перезапускает.
